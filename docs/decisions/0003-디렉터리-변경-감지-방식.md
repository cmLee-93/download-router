# ADR 0003: 디렉터리 변경 감지 방식

## 상태

채택

## 배경

Download Router는 지정된 디렉터리에 새 파일이 추가되는 시점을 감지해야 한다.

백그라운드에서 계속 동작하는 프로그램이므로 다음 조건을 고려했다.

- 변경이 없을 때 낮은 자원 사용
- 브라우저 외 프로그램이 생성한 파일도 감지
- Windows 전용 네이티브 코드 최소화
- Java 코드만으로 구현 및 유지보수 가능

## 결정

디렉터리 변경 감지에는 Java NIO의 `WatchService`를 사용한다.

초기 구현 범위는 다음과 같다.

- 사용자가 지정한 단일 디렉터리 감시
- `ENTRY_CREATE` 이벤트 수신
- 별도 백그라운드 스레드에서 이벤트 대기
- 애플리케이션 종료 시 감시 서비스 종료

`WatchService`는 신규 파일 후보를 감지하는 역할만 담당한다.

다운로드 완료 판정과 실제 파일 처리는 별도 로직으로 분리한다.

## 이유

- 변경이 없을 때 디렉터리를 반복 조회하지 않는다.
- Java 표준 API만으로 구현할 수 있다.
- 파일 생성, 수정, 삭제 이벤트를 지원한다.
- JNI 또는 JNA와 같은 네이티브 연동이 필요하지 않다.
- 감지 방식과 파일 처리 로직을 분리하기 쉽다.

## 고려한 대안

### 1. 주기적 디렉터리 스캔

일정 주기로 파일 목록을 조회하고 이전 상태와 비교한다.

- 장점
    - 구현이 단순하다.
    - 파일 시스템 이벤트 지원 여부에 덜 의존한다.
- 단점
    - 변경이 없어도 디렉터리를 반복 조회한다.
    - 파일 수가 증가하면 비교 비용도 증가한다.
    - 검사 주기만큼 감지가 지연될 수 있다.

### 2. 브라우저 확장 프로그램

브라우저의 다운로드 이벤트를 애플리케이션으로 전달한다.

- 장점
    - 브라우저 다운로드 완료 시점을 직접 확인할 수 있다.
- 단점
    - 브라우저별 확장 프로그램이 필요하다.
    - 별도의 설치 과정이 필요하다.
    - 브라우저 외 프로그램이 생성한 파일은 감지할 수 없다.

### 3. Windows 네이티브 API

Windows 파일 변경 알림 API를 JNI 또는 JNA로 호출한다.

- 장점
    - Windows 파일 시스템 기능을 직접 제어할 수 있다.
- 단점
    - Windows 종속성이 증가한다.
    - 네이티브 연동과 배포 구성이 복잡해진다.
    - 현재 요구사항에 비해 구현 비용이 크다.

## 채택에 따른 영향

`WatchService` 채택으로 다음 추가 처리가 필요하다.

- `ENTRY_CREATE`만으로 다운로드 완료 여부를 판단할 수 없음
- `.crdownload`, `.part` 등 임시 파일 제외 처리 필요
- 파일 크기 변화와 파일 사용 상태 확인 필요
- 임시 이름에서 최종 이름으로 변경되는 경우 처리 필요
- `OVERFLOW` 발생 시 디렉터리 재검사 필요
- 애플리케이션 시작 시 기존 미처리 파일 확인 필요
